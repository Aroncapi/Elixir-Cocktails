PENDIENTE #1 - EUREKA SERVER NO ARRANCA -> RESUELTO (sesion 2, fix aplicado)
  Sintoma: mvn spring-boot:run falla con
     "No qualifying bean of type
      'com.netflix.discovery.shared.transport.jersey.TransportClientFactories'"
  Causa raiz (confirmada con el reporte --debug de Spring):
     la clase principal NO tiene @EnableEurekaServer.
     Initializr solo genera @SpringBootApplication. Sin esa anotacion no se
     crea EurekaServerMarkerConfiguration$Marker y por lo tanto no se activa
     EurekaServerJerseyClientAutoConfiguration (que es la que publica los
     beans de transporte HTTP de Eureka).
  FIX: anotar la clase principal de eureka-server con @EnableEurekaServer.
  Archivo: eureka-server/src/main/java/com/barpro/eureka/EurekaServerApplication.java
  Despues re-ejecutar y verificar: http://localhost:8761/actuator/health

  Contexto util si vuelve a fallar (diagnostico completo):
  - Spring Cloud Netflix 5.0.2 tiene 3 transportes para EurekaClient:
      Jersey   -> se activa si existe clase org.glassfish.jersey.client.JerseyClient
                  (si: eureka-client-jersey3 la trae) y eureka.client.jersey.enabled
                  no este en false
      RestClient -> solo si jersey NO esta presente o eureka.client.jersey.enabled=false
                    (clase org.springframework.web.client.RestClient, esta en spring-web)
      WebClient  -> si hay clase WebClient (spring-webflux) y no este deshabilitado
  - En nuestra app: jersey SI esta, asi que la rama RestClient queda bloqueada.
  - Si un cliente (auth/core/notification/gateway) diera el mismo error,
    probar primero: eureka.client.jersey.enabled=false  (fuerza la rama RestClient)
    o agregar spring-boot-starter-restclient al pom.
  - Diagnostico reproducible con:
      mvn spring-boot:run "-Dspring-boot.run.arguments=--debug"

7. ARQUITECTURA RESUMEN
--------------------------------------------------------------------------------

  Angular 22 (HTTPS)
        |
        v
  gateway :8080  (Spring Cloud Gateway + validacion JWT, unico puerto expuesto)
        |
        +--> auth-service :8081         (login, usuarios, roles, JWT)
        +--> core-service :8082         (cocteles, tipos de evento, servicios/
        |                                tiers, solicitudes #REQ, clientes,
        |                                cotizador publico, desglose, PDF)
        +--> notification-service :8083 (preview wa.me, log de notificaciones;
                                         API WhatsApp oficial = fase 2)
        |
  eureka-server :8761 (descubrimiento de servicios)

  MySQL 8 (Docker): auth_db | core_db | notif_db  (database-per-service)

  JWT: auth-service emite (HS256, secreto compartido por variables de entorno),
       gateway valida y propaga headers X-User-Email / X-User-Role.

  Rutas publicas sin login (paso 3 del cotizador):
    POST /api/public/solicitudes            (crea solicitud -> folio #REQ-xxx)
    GET  /api/public/solicitudes/{token}    (link de seguimiento del cliente)

  ENTIDADES PRINCIPALES (core-service):
    Cocktail        nombre, categoria, ingredientes, imagen, activo,
                    tipos de evento recomendados
    EventType       Bodas, Corporativos, Fiestas Privadas, Masterclass, ...
    ServiceTier     Servicio Base (horas + pax), Menu Premium,
                    Personal adicional (bartenders)
    Client          nombre, email, whatsapp, ubicacion, tier
                    (VIP/Corporativo/Particular), gasto acumulado
    Request         folio #REQ-xxx, cliente, tipo evento, fecha/hora,
                    invitados, duracion, ubicacion, cocteles seleccionados,
                    desglose (base + premium + personal), total,
                    estado (PENDIENTE/CONFIRMADO/CANCELADO), token publico

8. DECISIONES DEL PROYECTO
--------------------------------------------------------------------------------

- Arquitectura: Microservicios (practica/CV)
- Base de datos: MySQL ahora -> PostgreSQL despues (Flyway desde el dia 1,
  SQL portable sin ENUM, para migrar cambiando 1 dependencia)
- WhatsApp fase 1: enlace wa.me gratis (mensaje pre-llenado con cliente,
  tipo de evento, fecha, cocteles y total). Fase 2: WhatsApp Business Cloud
  API de Meta (verificacion Business + template aprobado + metodo de pago;
  Mexico ~0.0085 USD por mensaje utility; primeros 1000 service/mes gratis).
- UI: seguir el DESIGN.md de los wireframes Velvet & Gilt
  (fondo #0d141d, dorado #D4AF37, texto #dce3f0, Playfair Display + Inter,
  esquinas rectas 0px, bordes dorados 1px, layouts split-screen)
- El negocio NO tiene inventario: es servicio de mixologia preparado en el
  evento (esto corrige una version vieja de esta nota)
- Despliegue nube (fase 7): Railway (~5 USD/mes) o Render (free tier),
  frontend en Vercel/Netlify gratis.
